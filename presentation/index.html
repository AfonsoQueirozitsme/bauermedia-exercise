Automated Web Hosting with Terraform & K3s

AWS K3s Cluster IaC

01. Objective & Requirements

  • Deploy a self-contained, automated environment.
  • Implement a K3s cluster (Control Plane + Worker).
  • Host a functional website with Load Balancing.
  • Utilize Infrastructure as Code for repeatability.
  • Demonstrate structured thinking and rational decisions.

02. System Architecture

Cloud Provider: Amazon Web Services (AWS)

Compute: 2x EC2 t4g.small (ARM Graviton)

Network: VPC with 2 Public Subnets

Security: Security Groups

Entry Point: Application Load Balancer (ALB)

03. Network & Security

Designed for Isolation and Availability:

Protocol/Port Purpose Source
TCP 22 SSH Management Admin IP
TCP 80 HTTP Traffic Public
TCP 6443 K8s API Server Cluster Nodes
TCP 30080 NodePort Exposure Load Balancer

04. Infrastructure as Code

Full automation via Terraform:


resource "aws_instance" "k3s_master" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t4g.small"
  key_name      = aws_key_pair.k3s_key.key_name
  user_data     = local.master_script
}
  • Dynamic SSH key generation via AWS Key Pair.
  • Automated Ubuntu 22.04 ARM AMI discovery.
  • Implicit dependencies (Worker waits for Master IP).

05. Kubernetes Layer: K3s

Why K3s?

  • Lightweight (single binary, < 100MB).
  • Fully compatible with K8s manifests.
  • Perfect for AWS Graviton ARM efficiency.

Bootstrap:


# Cloud-init on Worker
curl -sfL https://get.k3s.io | K3S_URL=https://${MASTER_IP}:6443 \
K3S_TOKEN=${SECRET} sh -

AWS Application Load Balancer:

  • Public: Port 80 (DNS name).
  • Target Group: Master & Worker EC2 (Port 30080).
  • Health Check: HTTP on /.
  • Multi-AZ: Deployed across 2 AZs.
Round Robin Policy

07. Technical Rationale

Decision: AWS Graviton (ARM) EC2
Rationale: Best performance/cost ratio with Graviton processors.

Decision: K3s + NodePort
Rationale: Reduces complexity by avoiding heavy Ingress Controllers for a demo scale.

Decision: Terraform TLS Provider
Rationale: Zero-dependency deployment — no need for pre-existing SSH keys.

08. Main Challenge & Resolution

The Challenge: Synchronizing the K3s cluster bootstrap in a single-pass deployment without manual secrets management.

  • The Worker node must know the Master's Private IP and Join Token before the K3s service starts.
  • The Resolution: Used Terraform's implicit dependency graph to inject the Master's IP directly into the Worker's cloud-init script.
  • The Result: A fully "Zero-Touch" deployment where the cluster is operational 120 seconds after terraform apply.
